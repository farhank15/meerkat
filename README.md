# Meerkat

### Your suite is green. But is it *meaningful*?

Meerkat scores how strong your test suite really is with the **Test Strength Index
(TSI)** — and shows the evidence behind every number.

## Green is not the same as meaningful

A passing check tells you a test ran. It doesn't tell you whether that test covered
the requirement you just changed, or whether it passed because the app works — or
because the assertion was too weak to ever fail.

Meerkat is a quality lens on top of an automated test run — it adds the
interpretation layer a green checkmark can't provide on its own: **does this
passing suite actually match the requirements it was written against?**

## What Meerkat does

- **Scores suite strength, not just pass/fail.** Coverage, stability, and pass rate
  fold into one deterministic number — the **Test Strength Index (TSI)**.
- **Traces every number.** Run detail shows the coverage table (every `SPEC.md`
  scenario ID with `covered` / `gap`), the TSI source breakdown, the audit trail,
  and commit traceability. Nothing is unexplained.
- **Interprets passing results against the contract.** The Verdict-Trust Gate and
  the Vacuous Auditor classify how each pass is anchored to the contract, and
  surface results that deserve a closer look (for example, checks that no longer
  assert meaningful behaviour) — before a team or an agent acts on them.
- **Keeps a live record of runs.** Each CI-reported run lands in Postgres through a
  workspace-scoped ingest endpoint; the dashboard, the run history and the public
  badge read directly from it.
- **Shares publicly, on purpose.** Any project can be published to a read-only
  scorecard at `/share/<slug>`. Private projects return a clean not-found — never a
  login wall, and never someone else's data.
- **Runs from your own artifacts.** The companion `suitevitals score` CLI scores a
  TestSprite JUnit result against a `SPEC.md` contract. Same input → byte-identical
  output.

## A workspace, not a demo account

Meerkat is multi-tenant from the first request. One account owns exactly one
workspace, and a workspace owns its projects, runs and keys — there is no shared
pool of sample data and no cross-account view.

- **Onboarding is four steps.** Name the workspace, create the first project, mint
  the first API key, copy the workflow file. The app does not open onto an empty
  dashboard with no next action.
- **Keys are generated by Meerkat.** Every key is `mk_live_…`, scoped to `ingest`,
  `read` or both, and expires in 30 days, 90 days, a year — or never. The secret is
  shown once and stored only as a hash; revoking is immediate.
- **Two surfaces, one account.** The console at `/dashboard` is the workspace view.
  The public surface at `/share/<slug>` is what you hand to a reviewer: latest TSI,
  run history, and the failing assertions, with no sign-in.
- **Agents get their own door.** An MCP server exposes the verdict, coverage gaps
  and assertion-quality findings, so a coding agent reads the evidence before it
  touches code.

## The Test Strength Index

```
coverage        = covered_ids / total_ids          # SPEC.md scenario IDs ↔ test names
stability       = 1 − conflicted/tested            # <2 runs → 1.0 (labelled estimated)
pass_rate       = meaningful_passes / total_tests
TSI             = round(100 × (0.50×coverage + 0.30×stability + 0.20×pass_rate))
```

Every formula is deterministic — **the same run data always produces the same TSI,
byte for byte.** No timestamps, no randomness inside the score. The committed
baseline (`SV-TSI-01`: coverage 30/33, stability 65/67, pass 63/67) scores **93**.

## How Meerkat and TestSprite fit together

Meerkat is a **consumer of TestSprite's results, not a replacement for them** —
one layer higher in the pipeline:

- **TestSprite creates and runs the tests** — the GitHub App check runs the suite
  against each PR's preview deployment and reports the required `TestSprite V3`
  check; branch protection on `main` keeps every merge gated on that green result.
  This is the primary path and needs no Starter upgrade.
- **Meerkat interprets and records the runs** — after each run, free read-only CLI
  calls (`test list`, `test result --history`, `test failure summary`) let Meerkat
  retrieve per-test verdicts, step-level facts, and failure bundles, reporting the
  run into its Postgres datastore through the key-gated `POST /api/runs` — the same
  source the public scorecard reads.

One pipeline, two roles: **TestSprite proves the product. Meerkat gives every run
a strength score, an evidence trail, and an interpretation the whole team — and
any code-facing agent — can act on.**

## What the engine covers

The scoring engine is unit-tested with **Vitest + fast-check** (property-based). Key
areas:

| Area | Focus |
|---|---|
| **TSI** | Formula (exact fixture → **93**), rounding, determinism, delta |
| **JUnit** | Parsing counts, skips, malformed input (throws `parse-error`) |
| **Coverage** | Traceability (partial match, case-sensitivity, gap/orphan detection) |
| **Scoring CLI** | `scoreFromArtifacts` — deterministic score from JUnit + SPEC |

The scenario contract lives in [`SPEC.md`](SPEC.md) and is the oracle for coverage
traceability — every coverage number Meerkat reports traces back to a line in it.

## What the TestSprite suite covers

The suite is generated in the TestSprite 3.0 portal from `SPEC.md` plus the
per-feature plans, then runs against each PR's preview deployment. **12 families,
33 scenarios** — every one of them a contract with an exact expected value:

| Family | Scenarios | What it proves |
|---|---|---|
| **Smoke** | `SV-SMK-01` · `SV-SMK-02` | The scorecard renders without login; the health endpoint answers `200` |
| **Action configuration** | `SV-CFG-01` · `SV-CFG-06` | Default paths resolve; a draft PR still gets a check and a comment |
| **JUnit ingest** | `SV-ING-01` · `SV-ING-02` · `SV-ING-04` | Counts from the fixture; skipped tests stay in the denominator; malformed XML is `parse-error`, not a crash |
| **TSI formula** | `SV-TSI-01` · `SV-TSI-04` · `SV-TSI-06` · `SV-TSI-07` | The fixture scores 93; rounding is half-up; the same input is byte-identical; the delta is signed |
| **Assertion depth** | `SV-ADQ-01` · `SV-ADQ-02` · `SV-ADQ-03` | Depth is reported per test; a vacuous pass is excluded; a shallow pass is flagged, not penalised |
| **Coverage traceability** | `SV-COV-01` · `SV-COV-04` · `SV-COV-09` | Partial match yields `30/33`; matching is case-sensitive; the table lists all 33 rows and the orphans |
| **Ratchet** | `SV-RAT-01` · `SV-RAT-03` · `SV-RAT-06` | A drop blocks the merge; a rise moves the baseline; the two checks stay separate |
| **PR comment** | `SV-PRM-01` · `SV-PRM-02` | The comment carries the score and the delta; a second push edits it in place |
| **Verdict trust** | `SV-VDT-01` · `SV-VDT-02` | A refusal is not a failure; an incomplete rerun withholds the score |
| **Spec drift** | `SV-DRF-01` · `SV-DRF-03` | Drift is distinguished from a regression; a spec-only PR is neutral |
| **Audit trail** | `SV-AUD-01` · `SV-AUD-02` · `SV-AUD-03` | The score traces to the JUnit rows, a gap traces to its `SPEC.md` line, provenance pins the commit |
| **Auto-remediation loop** | `SV-FIX-01` · `SV-FIX-02` · `SV-FIX-04` · `SV-FIX-06` | A regression is fixed and goes green; a refusal is never auto-fixed; drift updates the test; one attempt, then a human |

The families that describe the CI loop (ratchet, PR comment, auto-remediation) are
exercised by the workflow in this repository; the product families run against the
deployed app.

## Honest by design

Meerkat does not invent data. Stability needs two runs of the same SHA; with one
run it reports `1.0`, labelled *estimated*. Coverage is ID-based — it matches
`SPEC.md` scenario IDs against test names, so it stays a testable contract instead
of depending on how any generator happened to name its files. When a project has no
ingested run, the score reads `n/a` and the badge says `n/a` — a dash is not a
zero, and a missing run is never rendered as a good one.

Accounts, workspaces, projects, keys and runs live in Neon (Postgres) via Drizzle.
CI reports runs through the scoped `POST /api/runs` endpoint; the dashboard, the
public scorecard and the badge are served from the database. Sign-in supports
password accounts and GitHub OAuth. The scoring engine itself stays pure and
database-independent.

![Test Strength Index](https://meerkat-app.vercel.app/api/badge/tsi.svg)

What is **proven** and what is still a **hypothesis** is tracked in
[`VALIDATION.md`](VALIDATION.md) — including the experiment that could falsify the
metric, and the maturity gates the project has not passed yet.

## Roadmap v2 — from verdict ledger to quality governance

The hackathon version ships the core loop. What follows is the product path
already hinted at by the shipped pieces — each v2 feature has a working seed
in this repo, not just a bullet:

| Seed shipped (works today) | v2 horizon |
|---|---|
| Failure bundles — failed rows coalesced by shared cause | Local LLM root-cause clustering over full failure bundles, proposed fixes as ready PRs |
| `gap-to-plans` — SPEC gaps emitted as ready-to-file test plans | Closed reverse loop: gaps auto-create TestSprite plans, runs auto-fill them |
| TSI trend across real PR waves | Time-series quality line per branch, "coverage grows, TSI must not go down" gates |
| ID-in-name contract matching | Semantic contract matching: tests matched to SPEC **intent** when naming conventions drift |
| Stability from same-SHA reruns | Flakiness risk scoring before a test even runs (async/time-dependent patterns) |
| Verdict-trust gate (green ≠ meaningful) | Mutation-testing score: inject bugs, measure whether the suite would actually catch them |
| Workspaces, scoped keys, public scorecards | Team roles, per-project quotas, audit log of key usage |

Guiding principle stays the same: Meerkat is a consumer of TestSprite's
results, not a replacement for them — the governance layer one level above the
pipeline.
